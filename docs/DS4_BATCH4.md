# DeepSeek V4.1: четыре независимых запроса на двух MI50

Статус: GPU/HTTP gates пройдены; проверенная сборка оставлена на стенде
29 октября 2026, 18:04 UTC. Это первый ограниченный B4-вариант с контекстом 8192
на запрос, а не подтверждение всех режимов и длинных контекстов.
Хронология, включая неуспешные проверки, находится в [рабочем журнале](DS4_BATCH4_PROGRESS.md).

## База и ограничения

База: 6c7c63052ef6ce82e49426b7cd93da6a55e8c4c6, опубликованная
YOCO 10/30 со сужающимся хвостом. Стенд: EPYC 7K62, 48 ядер / 96 потоков,
512 GB RAM, две MI50 по 32752 MiB. GPU0: trunk 0–9 и три MTP; GPU1:
trunk 10–39 и head. Общие веса, экспертные кеши, CPU-пулы и рабочая память
исполнения; четыре независимых истории запросов. Квантование весов/KV,
число выбранных экспертов и формула целевого sampler не менялись.

Резидентная ёмкость первого выпуска — 8192 токена на запрос, включая
prompt и максимальный ответ. Это не обещание четырёх контекстов по 262144.
Исходная большая рабочая арена пока сохраняется. Аллокации проверяются
отдельно на каждой GPU; нехватка памяти не скрывается сокращением контекста.

Изображения, logprobs и неподдерживаемые penalties отклоняются до изменения
состояния. Автоматическая миграция solo↔batch отключена согласованной
capability; все HTTP-запросы обслуживаются через слоты.

## Что изменено

- `src/dsv41/ds4_model.cu/.hpp`: RequestHostState, request-local KV/rings,
  compressor partials и snapshots, изображения, токены, позиции, sampling-q;
  создание/переключение/освобождение арен с поколениями. Общие веса не копируются.
- `ds4_request_state.hpp`: проверяемые границы состояния/ёмкости.
- `ds4_batch_execution.hpp`: владение CPU accounting независимо от изменяемого
  активного request state; завершения worker не обращаются к уже сменённой арене.
- `ds4_batch_serve.inc`, `ds4_batch_request.hpp`: один владелец GPU execution,
  очередь команд, ограниченный admission, отмена, независимые RNG и терминальные
  события после завершения работ. Строгая проверка отрицательных/устаревших слотов.
- `serve/ds4_batch_protocol.py`, `serve/server.py`: версия протокола ds4-v2,
  события с поколением слота, ограниченная очередь пятого запроса, передача
  seed/next-draw через сегменты одного логического HTTP-запроса.
- `ds4_spec_segments.hpp`: разделение speculative batch на целые независимые
  сегменты суммарно не более kWin=16. Четыре verify по шесть строк — два прохода
  по 12 строк, а не переполнение 16-строчного scratch.
- `tests/dsv41/`: CPU lifecycle/RNG/границы и GPU state/logits oracles.

### Настоящий AR B4 и 2+2

Один packed pass объединяет rows независимых запросов в общих MoE/shared-expert
и head вычислениях. Attention, compressor, absolute positions и Engram остаются
сегментными. Это не четыре процесса и не четыре последовательных вызова step.

Режим 2+2 использует два отдельных PackedFrame и activation/handoff буфера.
GPU0 может продвигать вторую пару, пока GPU1 обрабатывает первую. Владелец
CPU-задач отделён от активной арены; staging source8 имеет подтверждение
завершения передачи перед повторным использованием. При числе готовых запросов
меньше четырёх используется общий AR batch соответствующего размера.
Замер ниже показывает общий elapsed эффект; отдельная временная линия
фактической занятости GPU в этой серии не снималась.

### Prefill и справедливость

Каждый scheduler tick сначала обслуживает готовый decode, затем не более
16 строк одного ожидающего prefill. Admission обходит слоты round-robin.
Так длинный новый prompt не удерживает GPU на один большой chunk.

Цена этого решения: маленькие feed-кванты не используют прежний большой
YOCO/cone prefill. При одиночном большом prompt возможна потеря prefill скорости.
Guard cone не ослаблен; произвольное дробление не выдаётся за сохранение его
ускорения. Этот вариант прежде всего обеспечивает совместное обслуживание.

### Многозапросный DSpark

Каждый запрос хранит собственную q distribution, sampling settings, seed/counter,
ring backups, compressor checkpoints и принятое продолжение. Draft выполняется
для каждого запроса отдельно, target verify объединяет сегменты; rejection
откатывает только соответствующую историю. Counter увеличивается по реально
выданным токенам; вставленные Python-сервером служебные токены не считаются RNG draws.

При объединении обнаружена смена арифметического пути: одиночные шесть строк
попадали в async MoE (порог 8), а 12 общих — в host-routed путь. Для малых
speculative-сегментов сохранён async путь при общей вместимости kWin.
Это исправление выбора пути, а не дополнительное квантование.
GPU-проверка этого исправления прошла: 32 побитовых сравнения.
После неё admission четырёх арен по 32768 отказал по резерву VRAM 128 MiB.
Для выпуска выбран явный предел 8192; эксперты не вытеснялись и резерв не
уменьшался. Это консервативный предел данной конфигурации, не доказательство
максимально возможного контекста. Предыдущие AR-замеры использовали cap32768.

Teacher-forced rows/s не являются скоростью выдачи текста. В HTTP учитывались
модельные токены отдельно от вставок thinking wrap-up. В одной проверке API
сообщил 128 completion tokens при 111 выданных моделью: оставшиеся были вставками.
Финальный короткий замер использует непрерывный ответ без thinking-сегментации
и сверяет API count с native emitted count. Пауза между HTTP chunks не равна
TPOT отдельного токена, если DSpark выдаёт несколько токенов вместе.

## Численная политика и пределы доказательства

Fixed-profile oracle нужен для одинаковых входных условий, это не production
исправление и не доказательство неизменности качества во всех режимах.
Первое неконтролируемое сравнение длинных префиксов расходилось ещё до packed
decode. Learned profile меняет порядок подкачки/разбиение вычислений; дальнейшая
FP-разница может менять routing. Сам профиль не заменяет router scores.

Сохранение квантованных весов не гарантирует bit equality при любом составе
батча: известны light-Q8/tiled-F16 dispatch и различия формы GEMM/накопления.
Ненулевой logit difference сам по себе не доказывает ухудшение качества.
Неуспешные gates не переименованы в PASS; широкий quality benchmark не выполнялся.

RNG проверен отдельно при фиксированных logits: запрос сохраняет seed/draw
независимо от соседей и транспортного разбиения. Старый B1 имел глобальный
counter между запросами, поэтому seeded текст старого процесса без фиксации
начального counter не является таким эталоном.

## Флаги и воспроизведение

`DS4_BATCH4=1` включает новый scheduler; `DS4_BATCH_CAP=8192` задаёт ёмкость
арены. `DS4_BATCH_PIPELINE22=1` разрешает проверенную топологию 2+2.
`DS4_BATCH_SPEC=1` отдельно включает многозапросный DSpark после его gate.
MTP должны оставаться загружены; AR означает отсутствие speculation, а не
удаление MTP из топологии YOCO.


HIP собирается существующими gfx906 флагами проекта. Опциональный
`STRATA_DS4_BATCH_SELFTEST=1` добавляет startup oracle:
`DS4_BATCH_SELFTEST=1` запускает его один раз после загрузки и до READY.
После него fixed-flow/diagnostic flags сбрасываются. В обычной сборке этот
entry отсутствует. CUDA/SYCL в этой работе не собирались.

### Проверенный финальный результат

Четыре HTTP-запроса действительно перекрывались: 4×64=256 модельных токенов,
9.534411 s, aggregate **26.850112 токена/s**, TTFT 2.010–2.642 s. Ответы при
одинаковом prompt/greedy sampling совпали. Native emitted count совпал с API.
108 speculative rounds, 176 offered, 144 accepted (81.82%); после начальных
четырёх токенов — 2.333 токена на round. Это сумма request-rounds, не GPU launches.
HTTP chunk-gap p95 305.44 ms; это не per-token TPOT.

Исходная служба с четырьмя конкурентными клиентами, обслуженными очередью:
256 API completion tokens за 8.467906 s, **30.231795 токена/s**; TTFT
